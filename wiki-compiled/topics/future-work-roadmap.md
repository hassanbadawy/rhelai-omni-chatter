# Future Work Roadmap

Forward-looking work explored in conversation but explicitly not yet implemented in `rhelai-omni-chatter`. Each item is paired with an honest "why not now" gate and a concrete first step for when the gate opens. The discipline matters: treating these as deliberate non-decisions (with a re-trigger condition) is the only thing that keeps a future-work list from rotting into wishful thinking.

## Summary [coverage: high -- 2 sources]

Four parallel streams of deferred work:

- **GitOps via ArgoCD** — replace ad-hoc `helm install` / `helm upgrade --reuse-values` with an ArgoCD ApplicationSet reconciling `helm/` from git. Why not now: the cluster is single-tenant, `helm upgrade --reuse-values` works, and ArgoCD adds a hard dependency on a sealed-secret/external-secrets path for the SA token.
- **Fresh-cluster bootstrap script** — a `bootstrap/install-prereqs.sh` that takes a bare OpenShift cluster to "ready for our helm charts" (cert-manager, KServe, Llama Stack operator). Why not now: no current customer is running install on a fresh cluster; CLAUDE.md and external RHOAI docs cover the few who do.
- **`llm-d` distributed inference** — replace single-node KServe `InferenceService` with `LLMInferenceService` (disaggregated prefill/decode, KV-cache-aware routing, multi-node TP) for models that exceed one GPU. Why not now: every model we serve (`qwen25-7b-instruct`, `gpt-oss-20b`) fits on a single GPU and is not GPU-bound at current load.
- **Wiki tooling roadmap** — a 3-phase plan to layer the Karpathy-llm-wiki ecosystem on top of `wiki/` without abandoning git as source of truth. Phase 1: install [`ussumant/llm-wiki-compiler`](https://github.com/ussumant/llm-wiki-compiler) as a Claude Code skill. Phase 2: dogfood [`zilliztech/memsearch`](https://github.com/zilliztech/memsearch) against the existing Milvus we ship to customers. Phase 3 (optional): an Obsidian MCP server when the wiki crosses ~50 pages. Why not now (per phase): Phase 1 needs verification it doesn't fight `scripts/wiki_lint.py`; Phase 2 is one more moving part with unclear retrieval lift on a small corpus; Phase 3 is infra in search of a problem at current scale.

The unifying rule: each entry has an explicit "why not now" gate. Items without a gate are not future-work — they're either current-work or noise.

## Architecture & Design [coverage: high -- 2 sources]

**GitOps via ArgoCD.** The target topology mirrors `alpha-hack-program/llm-d-guide`'s `gitops/` layout: an ArgoCD ApplicationSet at the cluster root, one `Application` per chart in `helm/`, sync waves encoding the install order (cert-manager → KServe → Llama Stack operator → `llama-stack` chart → `guardrails-orchestrator` → `llama-stack-ui` / `llama-stack-playground`). Helm value overrides move from `--set` flags into `values:` blocks in each Application spec. Cluster-truth secrets (the vLLM SA token, HF tokens) cannot be committed to git; they require sealed-secrets or external-secrets-operator pulling from a vault. The day-to-day workflow shifts from `helm upgrade --reuse-values` to `git commit + argocd app sync` — slower for one-off testing, but with a real audit trail and drift detection. Reference implementation: `https://github.com/alpha-hack-program/llm-d-guide` `gitops/` directory.

**`llm-d` `LLMInferenceService` vs current `InferenceService`.** llm-d (GA in RHOAI 3.3) replaces the single-node KServe `InferenceService` CRD with `LLMInferenceService`, which has first-class fields for disaggregated prefill/decode pods, a gateway routing layer, and KV-cache-aware request routing. From the application perspective, Llama Stack still consumes vLLM endpoints by URL + SA token, so the `vllm.url` / `vllm.apiToken` / `vllm.modelId` chart values stay the same shape. From the cluster perspective, the deployment pattern changes: `LLMInferenceService` + `ServingRuntime` + ModelCar OCI images instead of the current `InferenceService` with `storageUri: oci://...modelcar-...`. Both endpoint kinds can coexist registered as separate models in Llama Stack during a migration.

**Wiki tooling roadmap — three phases.**

- *Phase 1 — install `llm-wiki-compiler` as a Claude Code skill.* Drop-in over the existing `wiki/`. Adds `/wiki-ingest` (interactive single-source addition with auto-`sources/` placement), `/wiki-search` (backlink-aware keyword search), `/wiki-visualize` (interactive knowledge-graph browser), **coverage tags** (`[coverage: high -- 15 sources]`) on synthesized sections, and **time-decay warnings** (`⚠️` on claims older than 18 months). The coverage and decay signals directly attack two named problems with the pure-markdown pattern: low-confidence synthesis and silent rot. First step: install via the Claude Code plugin marketplace and run `/wiki-migrate` against `wiki/` to confirm idempotent integration. If it rewrites schema in ways that break `scripts/wiki_lint.py`, gate adoption on a config-only mode.
- *Phase 2 — dogfood Milvus by adding `memsearch`.* `memsearch` keeps markdown as source of truth and treats Milvus as a rebuildable "shadow index": SHA-256 dedup, hybrid BM25 + dense + RRF reranking, file-watcher-driven reindex on git pull. We already ship a Milvus chart at [`helm/milvus/`](../../helm/milvus/) for the Llama Stack RAG path, so pointing memsearch at the same Milvus instance costs nothing in infra and exercises the same vector store our customers run. Cross-tool memory falls out naturally — `wiki/` becomes queryable from Codex, OpenClaw, Cursor, not just Claude Code. First step: stand up memsearch against a *development* Milvus first (not the cluster Milvus); index `wiki/` end-to-end; measure whether semantic search beats `rg` on a corpus this small.
- *Phase 3 (optional) — Obsidian MCP for graphical browsing.* Triggered when `wiki/` crosses ~50 pages and the index-and-grep workflow stops scaling. The markdown is already Obsidian-compatible. Candidate servers: [`aaronsb/obsidian-semantic-mcp`](https://github.com/aaronsb/obsidian-semantic-mcp) (collapses 21+ tools into 5 AI-optimized ops, state-aware), [`jacksteamdev/obsidian-mcp-tools`](https://github.com/jacksteamdev/obsidian-mcp-tools) (semantic search + Templater), [`MarkusPfundstein/mcp-obsidian`](https://github.com/MarkusPfundstein/mcp-obsidian) (canonical Obsidian REST integration).

## Decisions & Rationale [coverage: high -- 2 sources]

**Skip managed memory services for the wiki (Mem0, Zep, Letta, Cognee, Cloudflare Agent Memory).** All of these pull the wiki off git-versioned markdown and into a SaaS knowledge store. Auditability and PR-reviewability are the substrate that makes the Karpathy llm-wiki pattern work — every dated entry, correction, and source frontmatter checksum has to survive `git log` and `git blame`. Managed memory services forfeit both. The decision is not "managed memory is bad"; it's "the wiki specifically must stay in git, so anything that moves it out is disqualified."

**Skip multi-agent research plugins (e.g. [`nvk/llm-wiki`](https://github.com/nvk/llm-wiki) `/wiki:research`, `/wiki:thesis`).** These spawn 5–10 parallel agents to *grow* a wiki autonomously from a thesis prompt. Useful when the wiki is still being built from scratch; less useful when the wiki already mirrors a working codebase that gets edited daily. Re-trigger: a research-heavy investigation lands (multi-week customer engagement deep-dive) where autonomous expansion would actually save time.

**Defer `llm-d` until single-GPU is the bottleneck.** Current models fit comfortably on one GPU. The `model-benchmarks.md` numbers show neither `qwen25-7b-instruct` nor `gpt-oss-20b` is GPU-bound at our load. llm-d's value (disaggregated prefill/decode, multi-node TP, cache-aware routing) only manifests when capacity or concurrency is the bottleneck. Adopting it now would buy operational complexity (gateway pods, prefill/decode split, cache routing) for benefits that don't show up until we serve a 70B+ dense model or push much higher concurrent load. Re-trigger: a customer requirement that exceeds one GPU.

**Defer GitOps until multi-cluster or stricter audit needs emerge.** The recurring pain points it would solve (`--reuse-values` carrying stale `vllm.url` across upgrades — pitfall 24; manual `oc set env` drift; install-order encoded only in CLAUDE.md) are real but tolerable on a single cluster with a small operator headcount. The cost (ArgoCD dependency, sealed-secrets workflow for SA tokens, slower one-off testing) is not. Re-trigger: a second long-lived cluster, or any externally-audited deployment.

## Operational Notes [coverage: high -- 2 sources]

When to revisit each item:

- **GitOps via ArgoCD** — when a second long-lived cluster appears (multi-cluster ops mean drift detection and a single audit trail go from nice-to-have to load-bearing), or when a customer-facing audit demands a git-traceable cluster state. First concrete action: copy `alpha-hack-program/llm-d-guide`'s `gitops/` directory shape, point it at our `helm/` charts for `llama-stack`, `guardrails-orchestrator`, `llama-stack-ui`, and validate `argocd app sync` reproduces the current hand-built state.
- **Fresh-cluster bootstrap** — when customer onboarding becomes routine (more than 1–2 fresh installs per quarter). The script bit-rots fast because every RHOAI release shifts CRDs and operator versions, so don't write it speculatively. Pin operator versions explicitly when written. First concrete action: `bootstrap/install-prereqs.sh` with idempotent `oc apply` / `helm install` for cert-manager, KServe, and the Llama Stack operator, in dependency order.
- **`llm-d`** — when a model we want to serve does not fit on a single GPU, or when concurrent load saturates a single InferenceService. Verify the cluster is on RHOAI 3.3+ first. First concrete action: deploy llm-d via the alpha-hack-program guide and stand up `qwen25-7b-instruct` as an `LLMInferenceService` *alongside* the existing `InferenceService`. Compare TTFT and throughput. Keep both endpoints registered in Llama Stack during the transition.
- **Wiki tooling Phase 1 (`llm-wiki-compiler`)** — trigger is whenever the wiki's "is this still true?" problem next bites (a stale claim shipped to a customer, a forgotten correction, a finding silently superseded). The coverage tags and time-decay warnings address that class directly. Low-cost to install; the main risk is layout opinionation.
- **Wiki tooling Phase 2 (`memsearch`)** — trigger is either (a) active Milvus debugging where dogfooding the same vector store the product uses would shorten the loop, or (b) cross-agent access (Codex, Cursor) becoming a real workflow, or (c) the wiki crossing roughly 50 pages where `rg` stops being enough.
- **Wiki tooling Phase 3 (Obsidian MCP)** — trigger is wiki size (~50+ pages) plus a real demand for graphical browsing. If neither materializes, this stays unbuilt indefinitely; that's fine.

## Pitfalls & Known Issues [coverage: low -- 1 source]

The standing risk in any deferred-work list is that "soon" never comes, and the rationale that justified deferral becomes outdated without anyone noticing. Specific failure modes:

- **Re-trigger conditions go stale silently.** "All current models fit on a single GPU" is true today; if it stops being true and nobody re-checks future-work, the team will rediscover llm-d the hard way during a capacity incident. Mitigation: revisit each entry annually and either (a) execute it, (b) re-state the gate with fresh numbers, or (c) delete it.
- **Reference implementations rot.** `alpha-hack-program/llm-d-guide` is pinned in the source `wiki/future-work.md` but external repos move. Verify the referenced `gitops/` and `scripts/` directories still exist and still implement the pattern described before relying on them.
- **Phased plans collapse into all-or-nothing.** The wiki tooling roadmap is explicitly staged so Phase 1 can land without committing to Phase 2 or 3. Resist the temptation to bundle them; each phase has its own gate for a reason.

## Findings & Measurements [coverage: high -- 2 sources]

- **2026-05-09 — Wiki tooling ecosystem survey (Karpathy pattern, 2026).** The Karpathy llm-wiki gist (April 2026) has produced an active tooling ecosystem in roughly a month. Survey across four buckets:
    - *Claude Code skills/plugins* (closest fit, install over our existing `wiki/`): [`ussumant/llm-wiki-compiler`](https://github.com/ussumant/llm-wiki-compiler) — most feature-rich, supplies `/wiki-compile`, `/wiki-capture`, `/wiki-ingest`, `/wiki-search`, `/wiki-lint`, `/wiki-query`, `/wiki-visualize`, plus coverage tags and time-decay warnings; [`kfchou/wiki-skills`](https://github.com/kfchou/wiki-skills) — `/wiki-init`, `/wiki-ingest`, `/wiki-query`, `/wiki-lint`, `/wiki-update`, `/wiki-audit` (per-page citation verification, closest analogue to our `sources/` discipline); [`Astro-Han/karpathy-llm-wiki`](https://github.com/Astro-Han/karpathy-llm-wiki) — single SKILL.md, multi-tool compatible (Claude Code, Cursor, Codex); [`nvk/llm-wiki`](https://github.com/nvk/llm-wiki) — multi-agent parallel research (5–10 agents), thesis-driven investigation, geared toward autonomously growing a wiki rather than hand-curating one.
    - *MCP servers for markdown vaults* (cross-tool access without leaving markdown): [`jacksteamdev/obsidian-mcp-tools`](https://github.com/jacksteamdev/obsidian-mcp-tools) (semantic search + Templater); [`aaronsb/obsidian-semantic-mcp`](https://github.com/aaronsb/obsidian-semantic-mcp) (collapses 21+ tools into 5 AI-optimized ops); [`MarkusPfundstein/mcp-obsidian`](https://github.com/MarkusPfundstein/mcp-obsidian) (canonical Obsidian REST integration).
    - *Markdown + shadow vector index hybrids* (RAG-without-RAG-architecture): [`zilliztech/memsearch`](https://github.com/zilliztech/memsearch) — strong fit because we already deploy Milvus via [`helm/milvus/`](../../helm/milvus/). Markdown stays source of truth; Milvus is a rebuildable shadow cache. Hybrid BM25 + dense + RRF reranking; SHA-256 dedup; file-watcher reindex on git pull. Install: `/plugin marketplace add zilliztech/memsearch`.
    - *Managed memory services* (Mem0, Zep, Letta, Cognee, Cloudflare Agent Memory): explicitly skipped. They pull the wiki off git, forfeiting auditability and PR-reviewability — the substrate that makes the pattern valuable.
    Action: the staged adoption plan in [`future-work.md`](../../wiki/future-work.md) "Wiki tooling roadmap" is the synthesis. Phase 1 (`llm-wiki-compiler`) is the highest-leverage drop-in; Phase 2 (`memsearch` against existing Milvus) is the dogfooding play; Phase 3 (Obsidian MCP) is conditional on scale.

- **2026-05-09 — Wiki bootstrap.** The legacy `llama-stack-ui/docs/` and `docs/` were merged into `wiki/`. `findings.md` was created as a new page; pre-existing dated observations live in [`pitfalls.md`](../../wiki/pitfalls.md), [`decisions.md`](../../wiki/decisions.md), and [`model-benchmarks.md`](../../wiki/model-benchmarks.md). This bootstrap is what made the future-work tooling survey possible — there was now a single canonical wiki for tools to layer on top of.
